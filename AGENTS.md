# Общие правила для обоих Codex

Правила действуют для всего репозитория. Мы разрабатываем один общий Telegram-клиент, а не два независимых приложения. Отвечай пользователю по-русски.

## Согласованный проект
- Первая платформа — Windows. Стек: C#, .NET 10 LTS, Avalonia, XAML, MVVM; тесты — xUnit.
- Подключение к Telegram — официальная TDLib через JSON-интерфейс и отдельный C#-адаптер. Не подменяй пользовательский клиент Bot API.
- Первая версия: авторизация, список чатов, история переписки и отправка текста. Звонки, стикеры и другие расширения не входят в начальную задачу.
- Начальный интерфейс: тёмная тема, список чатов слева, переписка справа, поле отправки снизу.
- Не меняй стек, архитектуру, версии основных компонентов и не добавляй зависимости без согласования с человеком.

## Единый каркас и границы
Репозиторий изначально пустой. Структура ниже — договорённость для первого каркаса, а не утверждение о существующих файлах.
- `src/TelegramClient.App/` — интерфейс, View и ViewModel; не содержит прямых вызовов TDLib.
- `src/TelegramClient.Core/` — общие модели и интерфейсы; не зависит от Avalonia и TDLib.
- `src/TelegramClient.Telegram/` — адаптер TDLib, авторизация и преобразование Telegram-данных в общие модели.
- `tests/` — тесты соответствующих компонентов; без реальных аккаунтов и секретов.
- Первый каркас создаётся одной согласованной задачей. Не создавай альтернативную структуру или второй клиент.
- UI-агент работает с интерфейсом; Telegram-агент — с интеграцией. Роль и границы конкретной задачи задаёт человек, а не сам агент.
- Общие модели, интерфейсы, файлы решения, конфигурация сборки и этот файл — совместная зона: изменения сначала согласуются.

## Совместная работа
- Перед работой прочитай `AGENTS.md`, вложенные инструкции и `docs/architecture.md`, если он существует; проверь `git status` и текущую ветку.
- Сначала обозначь план и список затрагиваемых файлов. Не расширяй задачу и не редактируй чужую зону без согласования.
- Не считай другую сессию Codex осведомлённой о текущем чате. Согласованные архитектурные решения сохраняй в `docs/architecture.md`.
- До параллельной разработки согласуй модели чата и сообщения, операции авторизации, загрузки и отправки, а также обработку обновлений и ошибок.
- Изменение общего контракта сначала предложи человеку: что меняется, почему и какую часть второго разработчика затронет.
- UI можно разрабатывать на тестовой реализации согласованного интерфейса. Не создавай несовместимый контракт ради временного обхода.

## Git и безопасность
- Каждый разработчик использует свою локальную папку и назначенную ветку. Не подключайте два агента к одной рабочей папке.
- Создание и переключение веток, commit, push, pull, merge и rebase выполняй только по явной просьбе человека. Не работай напрямую в `main` без разрешения.
- Не перезаписывай чужие изменения. Не используй force-push, `reset --hard`, `clean` и удаление файлов для обхода конфликтов без отдельного разрешения.
- Готовьте небольшие pull request с одной задачей; второй разработчик проверяет изменения перед объединением. Перед следующей задачей согласуйте обновление от `main`.
- Не добавляй в Git и не выводи в логи API-ключи, `api_hash`, коды входа, пароли 2FA, файлы сессий, базы TDLib и личную переписку.
- Секреты и пользовательские данные хранятся локально вне отслеживаемых файлов; до их создания настрой `.gitignore`. Примеры содержат только заглушки.
- Не выполняй вход в реальный аккаунт, отправку сообщений или другие действия в Telegram без явного разрешения человека.

## Качество и завершение
- Делай минимальные изменения в рамках задачи; не исправляй попутно несвязанные проблемы и не вводи лишние абстракции.
- Используй асинхронный ввод-вывод; не блокируй UI. Обрабатывай обновления TDLib в порядке получения и передавай UI-изменения в UI-поток.
- Ошибки обрабатывай явно; не скрывай сбои и не выдавай тестовые данные за реальное подключение.
- После изменений кода запускай `dotnet build` и `dotnet test` из корня после появления решения; добавляй относящиеся к задаче тесты в существующие тестовые проекты.
- Если проверка невозможна, объясни причину. Не заявляй об успешной сборке или работающей авторизации без фактической проверки.
- В конце перечисли изменения, результаты проверок и что нужно второму разработчику для интеграции. Не коммить и не отправляй изменения автоматически.
