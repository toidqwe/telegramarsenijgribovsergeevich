# Общие правила форка для обоих Codex

Мы разрабатываем один неофициальный форк Telegram Desktop. Правила действуют для всего репозитория; отвечай пользователю по-русски.

## Основа и приоритеты
- Согласованный стек: C++, Qt и CMake; первая платформа — Windows x64. C# / Avalonia / TDLib больше не используются.
- Базовый релиз и исходный commit зафиксированы в `docs/fork/upstream.json`. Сохраняй историю upstream, лицензии, уведомления и закреплённые submodule-ревизии.
- Прочитай `docs/architecture.md` и `docs/fork/README.md`. Технический справочник upstream сохранён в `docs/fork/upstream-agent-guide.md`; наши правила имеют приоритет.
- Не переноси инфраструктуру upstream: очереди `ai-tdesktop`, приватные CI, чужие секреты, автообновление и публикацию релизов. Не считай `out/` заранее настроенным.
- Актуальные требования Windows-сборки берутся из `docs/building-win.md` выбранного релиза, а не из устаревших примеров справочника.
- Не создавай второй клиент, собственный сетевой стек или альтернативный каркас. Сначала собираем исходную основу, затем добавляем по одной функции.

## Границы работы
- Перед изменениями прочитай применимые вложенные `AGENTS.md`, проверь `git status`, ветку и условия конкретной задачи.
- Перед добавлением C++-кода прочитай соответствующую запись `Telegram/SourceFiles/AGENTS.md`, ближайшую карту области и `REVIEW.md`.
- UI-роль: интерфейс, диалоги, история и настройки; интеграционная роль: API, данные, MTProto и хранение. Конкретную роль и список файлов задаёт человек.
- Общее: контракты, настройки и формат хранения, сборка, зависимости, branding и эти правила. Изменения сначала согласуются между разработчиками.
- Не редактируй чужую область без согласования; сначала сообщи, какие файлы и какую часть второго разработчика затронет изменение.
- Решения сохраняй в `docs/architecture.md`; другой Codex не обязан знать содержимое текущего чата.
- Сохраняй существующие функции, обработку ошибок и поддержку sponsored messages. Не обходи ограничения Telegram API.

## Git и сотрудничество
- У каждого разработчика своя локальная папка и отдельная назначенная ветка. Не запускайте два агента в одном рабочем дереве.
- Создание/переключение веток, commit, push и интеграция выполняются по просьбе человека; согласованная подготовка и публикация общей основы разрешены.
- `origin` — наш GitHub; `upstream` — Telegram Desktop. Никогда не отправляй наши изменения в upstream или в чужие submodule-репозитории.
- Не применяй force-push, `reset --hard`, `clean`, массовое удаление или перезапись чужих изменений для обхода конфликтов.
- Одна функция — небольшой pull request. Перед следующей задачей согласуйте обновление от `main`; ревизии submodules не обновляются автоматически.
- Обновления upstream интегрируются отдельной задачей: review, сохранение истории, сборка и тесты. Не выполняй `submodule update --remote`.

## Секреты и реальные аккаунты
- Не добавляй в Git и не выводи в логи API-секреты, коды входа, 2FA, `tdata`, базы, дампы или личную переписку.
- Личные API-реквизиты передаются локально через окружение; примеры содержат только заглушки. Публичный upstream test API допустим исключительно для локальной проверки сборки.
- Не входи в реальный аккаунт, не отправляй сообщения и не запускай действия с пользовательскими данными без отдельного разрешения.
- Перед распространением нужны собственные API-реквизиты, неофициальное название/логотип и выполнение GPLv3 / условий Telegram. Не публикуй тестовую сборку как готовый клиент.
- Сборка форка отключает официальное автообновление и отправку crash reports; не включай их без согласованной собственной инфраструктуры.

## Качество и завершение
- Минимальные изменения; без попутного рефакторинга, новых зависимостей и изменений основных версий без согласования.
- Сохраняй стиль upstream, UTF-8 без BOM и платформенные окончания строк; не переписывай весь файл ради форматирования.
- Не блокируй UI; учитывай lifetime асинхронных callbacks. Изменения бинарного хранения должны оставаться совместимыми.
- Проверяй через `scripts/check-windows.ps1`; сборка и зависимости запускаются явно по `docs/fork/README.md`. Изменения кода проверяй Debug-сборкой и относящимися к задаче тестами.
- Не выдавай наличие исходников за успешную сборку. Если отсутствует инструмент или проверка не пройдена, укажи точный блокер.
- В конце перечисли изменения, фактические проверки и инструкции для второго разработчика. Не публикуй релизы автоматически.
