# Архитектура общего форка

## Принятое решение

Используем исходный Telegram Desktop v7.4.1: C++, Qt и CMake. Ранее предложенный C# / Avalonia / TDLib-каркас отменён; не создаём его рядом с форком. Сеть, авторизация, хранение и существующий интерфейс остаются реализациями upstream.

Версия и commit записаны в `fork/upstream.json`. Интеграция сохраняет оригинальную историю и первый commit наших правил. `origin` — наш репозиторий, `upstream` — источник обновлений, но не место публикации наших изменений.

## Основные области

- `Telegram/SourceFiles/dialogs/`, `history/`, `ui/`, `settings/` — список чатов, переписка, общие UI-компоненты и настройки.
- `Telegram/SourceFiles/api/`, `mtproto/`, `data/` — запросы, транспорт и общие модели Telegram.
- `Telegram/SourceFiles/intro/`, `core/`, `storage/`, `platform/` — вход, жизненный цикл приложения, локальные данные и интеграция с ОС.
- `Telegram/Resources/` — строки, стили, изображения и другие ресурсы. Строки и размеры оформляются по правилам upstream, не хардкодятся в UI.
- `cmake/` и библиотеки `Telegram/lib_*` — закреплённые submodules. Не редактируем их как обычные файлы корневого проекта и не обновляем автоматически.
- `scripts/` и `docs/fork/` — наши проверка окружения, оболочка сборки и инструкции. `out/` — локальные артефакты, не Git.

Перед изменением C++-кода читаем атлас `Telegram/SourceFiles/AGENTS.md` и карту соответствующей области. Полный технический справочник upstream сохранён в `fork/upstream-agent-guide.md`; требования конкретного релиза в `building-win.md` имеют приоритет над его устаревшими примерами.

## Два разработчика

Предлагаемое разделение: один работает с UI, другой — с API, данными и интеграцией. Владельца и файлы каждой конкретной задачи подтверждает человек. Названия веток выбираются после синхронизации `main`.

Общие контракты, настройки, сериализация, CMake, submodule-ревизии и branding меняются отдельной согласованной задачей. Перед параллельной работой согласовываем описание функции, границы файлов и критерий проверки. При пересечении областей сначала согласуем изменение, а не делаем две несовместимые реализации.

## Проверка и границы готовности

Первый этап — воспроизводимая Debug-сборка неизменённой продуктовой основы на двух компьютерах. Только затем выбираем первую дополнительную функцию. В этой подготовке продуктовый C++-код не изменяется.

Оболочка Windows-сборки отключает официальное автообновление, crash reports и LTO. Публичный test API используется только по явному флагу для локальной проверки; реальный вход и действия с аккаунтом требуют отдельного разрешения.

Исходные release/bot/scheduled workflows перемещены в `.github/upstream-workflows/` как неактивный архив. Наш CI проверяет метаданные, синтаксис скриптов и валидацию локального API-cache; зелёная проверка не доказывает сборку или работу Telegram API.

Перед выпуском: собственное неофициальное имя и логотип, API-реквизиты, отдельная идентичность приложения и мест хранения, соблюдение GPLv3 / Telegram API Terms. Оригинальные `LICENSE` и `LEGAL` сохраняются. До этого не публикуем исполняемые сборки.
